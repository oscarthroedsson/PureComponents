A file field is two things in one box: a button, which we style through ::file-selector-button, and a line of text the browser writes beside it. The button's wording — Choose file, Browse…, Välj fil — comes from the browser and the operating system's language, and CSS cannot change it. So the <label> is not a formality here: it is the only place the words the user actually needs can go.

multiple is the whole difference. Pick more than one file and the browser writes 3 files instead of a name, and switches its own button text to the plural — both on its own, neither reachable from CSS. accept filters the file dialog; it is a convenience, not validation, and the server still has to check what arrives.

The button is pulled out to the box's inner edge by a margin that is exactly the field's own padding, negated — so it reaches the edges without adding height, and the field resolves to the same 1lh + padding + border an .pu-input does. A file field and a text field in one form are the same height, and neither was told what that height is.

file-sm, file-md (default), file-lg. The class rewrites one variable and the button follows, because font: inherit is what carries the size across into the pseudo-element. It is a leaf, so the class here resizes only this control — put it on .pu-form, .pu-fieldset or .pu-field to move a whole group.

file-sharp, file-smooth (default), file-rounded. The button's leading corners take the box's inner radius — the outer radius less the border's width — so a rounded field ends in a half-circle that meets the border rather than cutting across it.

file-ghost removes the field's box, not the control inside it — the same thing it means on .pu-input. The button keeps its surface, and closes its own shape, because with no border around it there is no longer an edge for its flat side to sit against. For a file field inside a surface that already reads as a box; never on its own, where a borderless field says nothing about where to click.

Same .pu-input-group and same .input-icon as .pu-input and .pu-select — but the end slot only. The button is drawn hard against the start edge, so a mark placed there lands on top of it and covers the browser's own label. There is no padding that can move a pseudo-element out of the way. This is the mirror of .pu-select, where the chevron owns the end and the icon gets the start. The icon is a real element drawing in currentColor, so it follows :disabled like every other control's does — the second field below is disabled, and the mark greys with it. An icon inside the button would have to be a background image with its colour baked in, and would stay at full strength on a greyed-out field, which is why there isn't one.

Hover anywhere in the box and the button reacts, because the whole box opens the dialog — not only the button. readonly has no branch on purpose: a file input matches :read-only whether or not the attribute is there, so it is useless as a condition, and copying .pu-input's :not(:read-only) guard would have cancelled hover entirely. Locking a chosen file is disabled.

Nothing in CSS can read a file's name or count — that needs JavaScript, and the library ships none. There is exactly one exception: an empty required file field is :invalid and a filled one is :valid. That is the only route to "has a file been chosen". This file does not paint it — there is no green anywhere else in the library and a file field is not the place to invent one — but the hook is native and yours to use. Every measurement comes from --form-*, so the group decides and the file field follows — no class on the control at all. The second form below is .pu-form.lg.rounded and the third rewrites one variable inline.

The button's surface, text, divider and gap are all variables, so a consumer can retune it without a second class. The file name's colour is the field's color — the button does not inherit it, which is the one lever we have over text the browser writes.
