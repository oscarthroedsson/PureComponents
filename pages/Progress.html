The native <progress> element already exposes its value and max to assistive technology, so it needs no aria-valuenow, aria-valuemin or aria-valuemax — those only go stale. A <label for> or an aria-label is all that is required.

One colour drives the whole bar. The fill is that colour and the track behind it is the same colour at low opacity, so there is never a second value to keep in sync — and the track lightens on a light page and darkens on a dark one by itself.

data-color takes a design token: primary (default), success, error, warning, info.

data-color is for the names we know. An arbitrary colour comes in through --progress-color, which takes anything CSS understands — hex, hsl, oklch, a named colour, another variable — as plain markup, no JavaScript. --progress-track-color overrides the track on its own if the derived one is not wanted.

--progress-color wins over data-color. With neither given, or a data-color that is not a name we know, the bar falls back to primary.

Three sizes: sm, md (default) and lg.

sharp, smooth and rounded (default). The fill inherits the radius from the bar, so it never has to be repeated per browser engine.

A <progress> with no value is indeterminate: work is happening, but how much is left is unknown. The sweep uses the same colour as a filled bar. Under prefers-reduced-motion it settles into a plain track rather than a still sweep, which would read as a half-filled bar.

Keep the number out of the label — "Uploading" stays true, "Uploading: 45%" is a lie the moment the value moves. The readout goes in visible text beside the bar, where sighted and screen reader users get the same thing.

.pu-progress-bar is for what the native element cannot do — content inside the bar, segments, a fill driven on its own terms. It takes the same data-color and custom properties, and it is the one case that needs the ARIA the native element gets for free: role="progressbar" with aria-valuenow, aria-valuemin and aria-valuemax, kept in sync by whatever moves the fill.
