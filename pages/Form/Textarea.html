The key alone is already md. Width comes from the parent; height comes from rows, and nothing here overrides it. Without rows the box falls back to two lines, so a bare textarea is visibly not an input.

sm · md · lg — 12 / 14 / 16px. Only the font size is set; the padding and the height floor are in em and follow it.

Same three shapes as every other control, from the same channel.

data-sizing="content" makes the box follow what is typed into it — type into the first one and watch it grow, delete and watch it shrink. No JavaScript, no scroll-height measuring, no hidden mirror element. The second one stops at --textarea-max-block-size and scrolls after that. Where field-sizing is not supported the declaration is ignored and the box keeps its rows height, which is why the attribute stays on the element.

Vertical by default: the browser allows both axes, and dragging a textarea wider than the form pushes the layout apart. data-resize="none" exists for a box that grows on its own and has nothing to drag for — it is not a default, because someone at 200% zoom needs to be able to make the box bigger (1.4.4).

The same states as .pu-input, drawn the same way. A read-only field is not disabled: it takes focus, its text can be copied, and it is submitted. Only the cursor separates them.

Both come from field.css and work the same beside a textarea as beside an input. The message row is always there, whether or not it shows — that is what stops the page jumping when an error appears. It is hidden with visibility, never display, so the row is reserved and the text stays out of the accessibility tree until it is real. The reveal is the control's own state, matched two ways: :user-invalid for native validation and [aria-invalid="true"] for Zod, Yup and React Hook Form, which set no native constraints at all.

The whole point of the shared channel: one class on the .pu-form retunes both controls, and they stay the same field with a different number of lines.
