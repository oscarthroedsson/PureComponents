Its own file and its own key, because a label is its own thing. It appears inside a .field, inside a .fieldset, beside a checkbox, in a table cell — and it looks the same in all of them. Nothing owns it.

Both are correct: for= pointing at the control's id, or the control nested inside the label. The first is preferred — it survives the control moving, and it is what assistive tech handles best. for= must point at an id that exists; a label bound to nothing looks correct in review and announces nothing.

A bare <label> inside a .field gets nothing from us, and that is correct — it is the consumer's element until they say otherwise. This styling used to be written as .field > label, which reached an element carrying no key of ours. That is the one thing §4.1 exists to prevent.

No size class of its own. The label reads --form-font-size like everything else in the family, so .form.sm, .fieldset.lg and .field.sm all reach it without this file knowing that any of them exist.

A label cannot see the control it names — they are siblings, and CSS has no sibling-upwards selector. So the disabled case is written by whoever owns both, which is .field. The target still carries its key, so nothing without .label on it is touched. The disabled colour is exempt from contrast under 1.4.3, which is what makes it legitimate at 3.6:1.

The same label beside a checkbox and inside a fieldset. It brings no layout of its own — the container decides where it sits — which is why one file can serve all of them.

The text is the accessible name. The unit, the hint and the message are not part of it — those are aria-describedby, and field.css draws them. Putting them inside the label makes the announced name a paragraph.
