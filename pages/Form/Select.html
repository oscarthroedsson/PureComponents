A <select> is for choosing one of a set the consumer already knows. The first option is the empty one — value="" — so the field has no answer until someone gives it one, and required can then catch the case where they did not. A placeholder option is not a label; the <label> still has to be there.

Same .pu-field as every other control: label, hint, control, message. aria-describedby lists both ids — CSS cannot draw that connection, so it is markup the consumer owns. The message row is reserved whether or not it is showing, which is what stops the form jumping when it appears.

sm · md · lg. The key alone is already md. A select is a leaf, so a size class on it retunes only that control — to resize a whole group, put the class on .pu-form, .pu-fieldset or .pu-field.

sharp · smooth (default) · rounded — the same three shapes as the rest of the family, off the same channel.

Disabled is native and so is the invalid state — but :user-invalid only fires after the user has been in the field, which is why the JS path aria-invalid="true" is styled beside it and not as a fallback. A select has no read-only: readonly does nothing on it, and the way to lock a choice while still submitting it is disabled plus a hidden input, or a single option left. Hover darkens the border and nothing else; the focus ring comes from main.css, and this file only clears the browser's own outline for a mouse click, where :focus-visible never matches. Every value here is the one .pu-input uses — measured identical, because a disabled select beside a disabled text field has to be the same disabled field.

With appearance: none the menu is not in the page at all — the browser hands it to the operating system, which draws it in its own layer. That is why a select on macOS opens over itself: Apple's convention for a pop-up button is to put the current value under the pointer. No CSS reaches that menu. appearance: base-select is the only thing that changes it. The menu becomes an element in the page, anchored under the button, and then it is ours — fill, corner, shadow, the options, and the open and close. It is behind @media (hover: hover) and (pointer: fine) on purpose: a menu drawn in the page replaces the platform's own, and on a touch screen the iOS wheel and the Android list are the better controls. A mouse gets this; a finger keeps the picker it knows.

<optgroup label="…"> is the native way to break a long list into sections, and the group label is announced. It is not selectable and must never be used as a placeholder row.

multiple and size turn the control into an open list box — a different shape entirely, and it has to look like it belongs to the same family without being forced into the height of a one-line field. Multi-select is hard to operate: it needs a modifier key on a mouse and is easy to break on a touch screen. A group of checkboxes is usually the better answer.

Width comes from the parent, not from the longest option — otherwise one country name decides the layout of the whole form. Which means an option longer than the box has to be handled rather than allowed to stretch it.
